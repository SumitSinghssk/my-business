Micro-frontends are one of the most over-prescribed patterns in modern web engineering. They solve a real organisational problem, but they introduce real runtime costs. Here is how we decide when independent deployability is worth the complexity, and how we implement it when it is.

Start With the Org Chart, Not the Bundle

Micro-frontends are a response to Conway's Law. If a single team owns the whole product, a well-structured monolith with clear module boundaries will beat a distributed frontend on every metric that matters: performance, consistency and developer experience.

We only recommend splitting when at least two of these are true:

  • More than four autonomous teams ship to the same user-facing surface.
  • Teams need genuinely different release cadences, such as daily versus quarterly.
  • Parts of the product have different compliance or security boundaries.

Module Federation vs. Isolated Sub-Apps

We've shipped both approaches in production and each has a clear sweet spot.

ConcernModule FederationIsolated Sub-Apps
Shared dependenciesShared at runtime, smaller payloadDuplicated per app
Failure isolationWeaker, one bad remote can break the shellStrong, crashes stay contained
State sharingStraightforwardRequires explicit contracts
Best forTeams on a shared stackMixed stacks or strict isolation

The Contracts That Keep It Sane

Whichever approach we choose, three contracts are non-negotiable:

  1. A shared design system consumed as a versioned package, so every slice looks like one product.
  2. A typed event bus for cross-slice communication, instead of reaching into each other's state.
  3. A performance budget per slice, enforced in CI, so no team can quietly add 400KB to the shell.

Our Rule of Thumb

If the main problem you're solving is deployment coupling, micro-frontends are a strong option. If it's code organisation, invest in a modular monolith first. It's far easier to split a well-modularised app later than to reassemble a fragmented one.
