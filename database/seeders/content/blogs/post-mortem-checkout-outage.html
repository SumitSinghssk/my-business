On a Tuesday evening during a client's seasonal sale, checkout failed for 47 minutes. Roughly 18% of payment attempts returned errors at the peak. This is our blameless post-mortem: what happened, why our safeguards didn't catch it, and what we changed so it can't happen the same way again.

Timeline

Time (UTC)Event
18:02Routine deploy of the pricing service begins.
18:09Checkout error rate rises from 0.2% to 4%.
18:14Burn-rate alert pages the on-call engineer.
18:31Pricing deploy rolled back. Error rate does not recover.
18:42Database connection pool exhaustion identified as the cause.
18:49Pool limits raised and stuck connections recycled. Errors return to baseline.

Root Cause

The pricing deploy added a new query that, under sale traffic, held database connections for up to 900ms instead of 20ms. The checkout service shares the same connection pool. As connections were held longer, the pool emptied and checkout requests began timing out while waiting for a connection.

Rolling back the deploy didn't immediately help because thousands of slow requests were already queued and still holding connections.

Why Our Safeguards Missed It

  • Load tests used last month's traffic profile, which didn't include sale-level concurrency.
  • The query was fast in staging, where the relevant table had 2% of production's rows.
  • Shared connection pools meant a problem in one service became an outage in another.

“The deploy was the trigger. The shared pool was the cause.”

What We Changed

  1. Each service now has its own isolated connection pool with strict per-query timeouts.
  2. Load tests run against a traffic model refreshed weekly, including known peak events.
  3. Staging databases are seeded with production-scale, anonymised data for query-plan testing.
  4. Deploys during announced sale windows now require a second approver and a canary stage.

The Takeaway

No single person made a mistake here. The system allowed a routine change to cascade. Blameless post-mortems exist so we fix systems rather than look for someone to blame, and so the next team inherits the lesson instead of the outage.
