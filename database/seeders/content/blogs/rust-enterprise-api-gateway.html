Our API gateway handles more than 10 billion invocations a month. The original implementation, a Node.js reverse proxy with a stack of middleware, had served us well, but tail latency and infrastructure cost were climbing faster than traffic. Rewriting the hot path in Rust with Tokio and Hyper cut our gateway cloud spend by 64% and pinned P99 latency.

Why Not Just Tune the Existing Gateway?

We tried. Garbage-collection pauses were the dominant source of P99 spikes, and every optimisation we made bought a few percent at the cost of increasingly fragile code. The gateway's job is narrow: authenticate, rate limit, route and observe. That makes it an ideal candidate for a small, focused rewrite.

Scope Discipline

The rewrite succeeded largely because of what we left out:

  • No business logic. The gateway only knows about routes, tokens and quotas.
  • Configuration as data. Routes are loaded from a versioned config file and hot-reloaded without restarts.
  • Plugins through WebAssembly. Team-specific transforms run in sandboxed Wasm modules instead of the core binary.
async fn handle(req: Request<Body>, state: Arc<GatewayState>) -> Result<Response<Body>, GatewayError> {
    let claims = state.auth.verify(&req).await?;
    state.limiter.check(&claims.tenant_id)?;

    let route = state.router.resolve(req.uri().path())?;
    let response = state.upstreams.forward(route, req).await?;

    state.metrics.record(&route, response.status());
    Ok(response)
}

Shadow Traffic Before Cutover

For four weeks the new gateway received a mirrored copy of all production traffic. Responses were compared with the live gateway and discarded, which surfaced 23 behavioural differences, mostly around header casing and edge-case redirects, before a single customer was affected.

Would We Do It Again?

Yes, for this component. Rust's learning curve is real, and we wouldn't rewrite business services this way. But for a small, performance-critical piece of infrastructure with a stable scope, it paid for itself within a quarter.
